Your question first: does upgrading touch your files and apps?

Your documents, code, photos, browser profiles, VM disks and Samba share are not touched at all. The upgrade never goes near your home directory outside ~/.config and a few state folders.

Your config files are mostly left alone, but not entirely. The upgrader checks each config against a list of file fingerprints of every config Omarchy has ever shipped. If your file is byte-identical to one of those, it is treated as untouched stock and gets replaced with the new default. If you changed even one character, it is left exactly as it is. Anything it does replace is copied to <name>.omarchy-upgrade-to-quattro.<timestamp>.bak next to the original first.

Some of your apps get uninstalled. Roughly sixty packages that Quattro no longer ships are removed, and several are things you use daily: Waybar, Walker, Mako, SwayOSD, hypridle, hyprlock, playerctl, wiremix, pavucontrol, satty, the screen recorders, VLC, LocalSend, Zoom, lazydocker. Most are removed because Quickshell now does that job natively. A few, like VLC and Zoom, are simply no longer default and you can reinstall them in one command.

Claude Code is safe. The retired list includes the claude-code Arch package, but yours came from the native installer and lives at ~/.local/share/claude, so pacman never sees it.

The one thing that genuinely breaks is your desktop customisation. Waybar is gone, so this morning's bar work does not carry over. Your Hyprland config files stop being read once you reboot into Lua. Both need rebuilding, and section five below is that rebuild, written out.

What Quattro actually is

Four structural changes, each of which invalidates a different assumption your setup makes.

One shell process instead of eight programs

Quickshell now hosts the bar, launcher, menus, notifications, on-screen volume and brightness display, control panels, lock screen and polkit agent in a single long-running process. That single process replaces Waybar, Walker, Mako, SwayOSD, hyprlock, hypridle, swaybg and polkit-gnome. It is configured by one file, ~/.config/omarchy/shell.json, and extended by plugins that are ordinary git repositories dropped in ~/.config/omarchy/plugins/.

Omarchy moves from a git checkout into pacman packages

Today ~/.local/share/omarchy is a git clone you update by pulling. After the upgrade it is a symlink to /usr/share/omarchy, and Omarchy arrives as two Arch packages, omarchy and omarchy-settings. A pacman hook now blocks a bare sudo pacman -Syu and tells you to run omarchy update instead. Fresh defaults reach new users through /etc/skel; existing users get them through per-user migration scripts.

Hyprland is configured in Lua

Every .conf becomes a .lua: hyprland.lua, monitors.lua, input.lua, bindings.lua, looknfeel.lua, autostart.lua. Instead of sourcing Omarchy's defaults with source = lines, your hyprland.lua calls require("default.hypr.omarchy") and then loads your own modules after it, so Omarchy can improve its defaults without rewriting your files. Settings come through hl.config{...}, keybindings through o.bind(...), window rules through o.window(...). Hyprland on this machine already supports it: the stub file is at /usr/share/hypr/stubs/hl.meta.lua.

Generated theme state moves out of your config

~/.config/omarchy/current becomes ~/.local/state/omarchy/current. Your own themes, hooks, plugins and shell layout stay in ~/.config/omarchy, which is the folder Omarchy now explicitly expects you to keep in a dotfile manager. That split is good news for your stow setup: the generated churn leaves the repo.

Alongside those, Quattro adds a unified menu and launcher on SUPER + SPACE, text scaling across shell, GTK and terminals, a bar you can drag to any screen edge, three new apps (a Markdown editor, a video trimmer, a calculator), and swaps the default terminal to foot and the default Wi-Fi stack to NetworkManager.

Exactly what the upgrader does to files

The whole upgrade is one self-contained script, omarchy-upgrade-to-quattro, 2444 lines of it. Four rules govern everything it does under ~/.config.

RuleApplies toWhat happens to your copy
Refresh if unmodified Files whose contents match a fingerprint of any Omarchy default ever shipped Backed up, then overwritten with the Quattro default. A modified file never matches, so it is skipped.
Always copy The new entry points: the six hypr/*.lua files, hypr/.luarc.json, omarchy/shell.json, omarchy/extensions/omarchy-menu.jsonc Written unconditionally. If something is already there it is backed up first. None of these exist on your machine yet, so nothing of yours is at risk here.
Fill gaps only Everything else Quattro ships under config/ Copied only where you have no file at that path. Existing files are never considered.
Retire uwsm/env, uwsm/default, mimeapps.list, fontconfig/fonts.conf, omarchy.ttf, xdg-terminals.list, environment.d/fcitx.conf, the three Omarchy systemd/user units No longer shipped, so no new copy arrives. Your existing file stays where it is, doing nothing. Custom lines in uwsm/env are the exception: they get carried into a new uwsm/env.d/99-omarchy-upgrade-env.

The stow wrinkle

Six of your ~/.config entries are directory symlinks into ~/dotfiles, including hypr and omarchy. When the upgrader writes ~/.config/hypr/monitors.lua, it follows that symlink and the file lands inside your dotfiles repo, as an untracked file in the hypr stow package. That is convenient rather than harmful, but it means the repo will be dirty with roughly ten new files right after the upgrade, and you should not git clean in a panic.

The one real hazard is single-file symlinks. The refresh rule deletes the target before copying, and deleting a stow symlink silently unlinks that file from your repo. Only ~/.config/omarchy.ttf, ~/.config/mimeapps.list, ~/.config/starship.toml and ~/.config/herdr/config.toml are single-file links, the first two are on the retire list, and the rest are yours and modified, so on paper none of them get touched. Step 2 of the plan verifies that rather than trusting it.

Making the portrait monitor work

Two separate problems hide behind this question, and only one of them is hard.

The layout is a solved problem

Resolution, position, the 270 degree rotation, the scale 1 that keeps it sharp, and the workspace pinning are all handled by monitors.lua in step 6 of the plan. Hyprland's Lua config has direct equivalents for every line of your current monitors.conf: hl.monitor for the monitor and hl.workspace_rule for the pinning. Expect the first boot after the upgrade to show a wrong layout, because a stock monitors.lua lands before yours does, and expect it to be right again five minutes later.

The bar size is the hard part

Here is the actual physics of why this screen is awkward. The Lenovo is 1920x1200 across 25 inches, so about 90 pixels per inch, and it runs at scale 1 because anything below 1.0 draws oversized and shrinks to fit, which visibly softens text. The Samsung is 138 PPI at scale 1.25 and the laptop panel is around 140 PPI at scale 1.2. Run the numbers on a 28 pixel bar and it measures 0.31 inches on the portrait screen against 0.25 on the Samsung and 0.24 on the laptop. That 30 percent is exactly what you were fixing this morning.

In Quattro the bar height comes from a single shell-wide property read by every screen's bar surface, and the layout is a flat list applied to Quickshell.screens with no filter. There is no per-monitor key in shell.json and no theme setting that varies by output. So there are three honest routes.

There is a fourth route worth naming and dismissing: raising the Samsung and laptop scales so the Lenovo is relatively smaller. It works arithmetically and makes everything on your two good screens physically bigger, which is not a trade you want.

One useful thing Quattro adds here: omarchy display text size <px> moves the shell font, the GTK text scaling factor and your terminal font point size together, in one command, live. It is global rather than per-monitor, but it makes finding the compromise a matter of trying numbers rather than editing three configs.

The browser change is bigger than one default

That command is also what breaks your stow symlink

This is the concrete instance of the hazard flagged earlier. xdg-settings writes by creating a temporary file and moving it into place. Moving a file onto a symlink replaces the symlink. rm ~/.config/mimeapps.list
cd ~/dotfiles && stow xdg

Where it will actually hurt

Five specific things on this machine, in the order they will annoy you.

Your two-bar setup cannot be reproduced

This is the real loss. Quattro's bar is built once per screen from one layout, with no way to give one monitor a different set of widgets or a different size. The relevant code is a flat Variants { model: Quickshell.screens } with no filter, and the height comes from a single shell-wide property. So the compact bar you built for the portrait Lenovo this morning has no equivalent in stock Quattro. The section on the portrait monitor below lays out the three ways round it.

Your Claude traffic light needs two fixes

Custom bar modules survive in a good way: you can declare one inline in shell.json with type: "command", and it accepts Waybar-style JSON on stdout, so claude-status keeps its output contract. Two things do change.

First, the coloured dots. Your script emits Pango markup (<span color='#...'>), and the bar renders text through a Qt Text element, which reads HTML rather than Pango. Qt will strip the colour and leave you three identical dots. The fix is one substitution in the script: <font color="#...">, which Qt does understand.

Second, the update trigger. Today your Claude Code hooks fire SIGRTMIN+10 at Waybar for an instant repaint, with the 2 second interval as a safety net. Command modules have no signal input, only a timer, so the hook becomes decoration and the interval becomes the actual refresh rate. At 2 seconds you will not notice. Only class: "active" is honoured for styling, which is exactly what your idle-lock module already emits.

Your Retro 82 copy will overwrite the one Quattro ships

Retro 82 is not your theme, it is an Omarchy theme, and it has already been converted on the Quattro branch: a rewritten colors.toml in the new semantic names, and hyprland.conf replaced by hyprland.lua. You get that for free. The problem is that you also keep a personal copy of it at ~/.config/omarchy/themes/retro-82/, 35 files tracked in your dotfiles.

Switching themes in Quattro copies the official theme into place first, then copies your folder over the top, file by file. Your folder contains a colors.toml in today's format, so yours wins and the converted one is discarded.

Nothing breaks. There is a thorough compatibility path that maps the old ANSI names onto the new ones, mixes the bright variants out of the base colours, and works out light or dark from the background's luminance. What you lose is the hand-tuning. The clearest example: panel and surface backgrounds fall back to your color0, a grey-purple #303442, where the converted theme deliberately picks the navy #0a2540 that matches the rest of Retro 82.

Only two files in that folder are actually yours: retro-82.icls for JetBrains and retro-82.zed.json for Zed. The rest is a stale duplicate of the stock theme plus generated per-app files that Quattro rebuilds from templates anyway.

Your three genuinely custom themes are Event Horizon, Carbon and Rose Pine Dark. None has an upstream equivalent, so nobody converts those for you, and they will land on the compatibility path described above. That is fine until you actually switch to one. Note that no Quattro theme ships a shell.toml at all, so surface roles and sizing come from the shell's own defaults unless you override them yourself. Your per-theme waybar.css, walker.css, mako.ini, swayosd.css and hyprlock.conf files become dead files.

Your shell prompt stops following the theme

Your .bashrc picks a Starship profile by reading the current theme's name out of ~/.config/omarchy/current/theme.name, then loading ~/.config/starship/<name>-powerline.toml. Quattro writes that file to ~/.local/state/omarchy/current/theme.name instead. The old path stops being updated, so the lookup finds a stale name or nothing at all, falls through the if, and you silently drop back to the plain starship.toml. Nothing errors, your prompt just quietly stops matching your theme. One path in one line fixes it, and the same line is worth pointing at the new location rather than guessing.

The profiles themselves are fine. event-horizon-powerline.toml, event-horizon-plain.toml and the two Retro 82 ones are already named to match the theme folder names, and your oh-my-posh configs are named consistently too, though those are commented out and inactive.

hyprdynamicmonitors writes to a file nobody reads

It is configured to generate ~/.config/hypr/monitors.conf from Go templates when your monitor set changes. After the upgrade Hyprland reads monitors.lua, so the profile switching would silently stop working. It is currently disabled and inactive, so this costs you nothing today. If you ever want it back, the templates are yours to edit and only need to emit hl.monitor{...} calls instead of monitor= lines.

Some of your keybindings now collide with defaults

Quattro puts the merged menu and launcher on SUPER + SPACE and gives herdr, the tmux replacement it now ships, SUPER + CTRL + RETURN. You already have a herdr config in your dotfiles, so that one is a nice landing. Your SUPER + ALT + RETURN tmux binding still works. Anything of yours that clashes needs hl.unbind before rebinding, same principle as today.

The plan

Nine steps across three moments: what we do this week, what we do on release day, and what we do after the first successful boot. Every file is given with its full path and marked create or edit.

Scope decision, 11 August

Steps 1 to 6 are the committed path: get there safely, keep your keybindings, keep your default apps. The bar layout in step 7, the theme work in step 8 and the monitor sizing question are deliberately left until after the first boot, when we can see what Quattro actually does on these three screens rather than guessing. The monitors part of step 6 still gets written on the day, because without it your screens come up in the wrong arrangement.

Before release day

01

Commit everything and tag the pre-Quattro state

The dotfiles repo currently has uncommitted changes in hypr/hyprland.conf, hypr/monitors.conf and this morning's Waybar work. Get all of it committed so the Quattro port is a clean, reviewable diff on top of a known-good 3.8.4 setup, and tag it so you can always read the old config.

cd ~/dotfiles
git add -A
git commit
git tag omarchy-3.8.4-final
git push --follow-tags

Push needs your SSH key unlocked first: run ssh-add in a real terminal, since the ! prefix cannot take a passphrase.

While you are in the repos: pin the tool versions in any Veygr mise.toml that currently floats. From Quattro onward, omarchy update runs mise up as a routine step, so an unpinned Node or Python version can move under a project on a day you were only patching the system.

02

Snapshot the things the upgrader will not back up

Config files get their own .bak. Firewall rules, the package list and the Samba config do not. This writes them to one folder you can diff against afterwards.

Create /home/emmanuel/dotfiles/omarchy-extras/pre-quattro-snapshot.sh
#!/bin/bash
set -euo pipefail

out="$HOME/pre-quattro-$(date +%Y%m%d)"
mkdir -p "$out"

pacman -Qqe            >"$out/pkgs-explicit.txt"
pacman -Qqm            >"$out/pkgs-aur.txt"
pacman -Qq             >"$out/pkgs-all.txt"
systemctl --user list-unit-files --state=enabled >"$out/user-units.txt"
systemctl list-unit-files --state=enabled        >"$out/system-units.txt"

sudo ufw status verbose >"$out/ufw.txt"
sudo cp -a /etc/ufw     "$out/ufw-etc"
sudo cp -a /etc/samba   "$out/samba"
sudo chown -R "$USER" "$out/ufw-etc" "$out/samba"

virsh -c qemu:///system dumpxml win11 >"$out/win11.xml"

find "$HOME/.config" -maxdepth 2 -type l -lname '*dotfiles*' \
  -printf '%p -> %l\n' | sort >"$out/stow-links.txt"

echo "Snapshot written to $out"

Keep the folder outside the dotfiles repo so it never gets stowed. After the upgrade, diff the ufw and stow-links files: those two catch the two hazards, a lost firewall rule and a broken stow symlink.

03

Confirm a bootable snapshot exists

The upgrader takes a Snapper snapshot itself, but confirm the boot menu can actually reach one before you need it. You are on btrfs with limine and limine-snapper-sync, so this should already be true.

sudo snapper -c root list | tail -5
grep -c 'snapshot' /boot/limine.conf

If the second command returns 0, stop and fix that before upgrading. A rollback you cannot boot into is not a rollback.

Release day

04

Run the upgrade

Quattro ships its own upgrader, omarchy-upgrade-to-quattro, which is deliberately self-contained so it can be curled onto a 3.x machine. The dev channel URL published with the beta is https://omarchy.org/upgrade-to-quattro-dev; on release day the stable equivalent will be announced, and we use that rather than the dev one.

# confirm the URL from the release announcement first, then:
curl -fsSL https://omarchy.org/upgrade-to-quattro | bash

Do not pass --yes. Watch it. The steps that matter are the package removal transaction (read the list before confirming) and the theme refresh at the end. Expect it to want a reboot; take it.

Three things to do before starting, in this order:

supabase stop                          # twelve containers, one of them Postgres
virsh -c qemu:///system shutdown win11 # let Windows close its own files
df -h /                                # the script needs 10 GiB and stops if short
05

First boot triage

Straight after the reboot, before touching any config, answer four questions in order. Each has a fallback that does not involve rolling back.

  • Do all three monitors come up? Quattro copied a stock monitors.lua in, and your monitors.conf is no longer read, so expect the wrong layout on the first boot. That is step 6.
  • Is the bar there? If not, omarchy-shell-ipc plus journalctl --user -u omarchy-shell -b tells you why.
  • Does the VM still start? virsh -c qemu:///system start win11, then check the Samba mount from inside the guest.
  • Did the firewall keep your rule? sudo ufw status verbose and diff against the snapshot from step 2.

Also run ls ~/dotfiles/hypr/.config/hypr/ and ls ~/dotfiles/omarchy/.config/omarchy/. The new Lua files and shell.json should be sitting there as untracked files, having arrived through your stow symlinks. If they landed in ~/.config as real files instead, a symlink got replaced and we fix that before going further.

Then put your defaults back, before anything else

These four commands undo the three default-app changes and repair the symlink the first of them breaks. Do this before you start porting config, so you are testing bindings against the browser and terminal you actually use.

# Browser: the upgrade forced Chromium. This also fixes every web app binding.
xdg-settings set default-web-browser vivaldi-stable.desktop

# Terminal: the upgrade deleted your preference file, so foot took over.
printf '%s\n%s\n%s\n' \
  '# Terminal emulator preference order for xdg-terminal-exec' \
  '# The first found and valid terminal will be used' \
  'com.mitchellh.ghostty.desktop' > ~/.config/xdg-terminals.list

# Repair the mimeapps.list symlink that xdg-settings replaced with a real file.
cp --remove-destination ~/.config/mimeapps.list ~/dotfiles/xdg/.config/mimeapps.list
rm ~/.config/mimeapps.list && cd ~/dotfiles && stow xdg

Then confirm: xdg-settings get default-web-browser says vivaldi, SUPER + RETURN opens Ghostty, and ls -l ~/.config/mimeapps.list shows an arrow pointing into dotfiles. Worth adding xdg-terminals.list to the xdg stow package in step 9 so the terminal preference is version controlled next time.

Porting the configuration

# Qt renders the bar label as HTML, not Pango, so span colours are dropped.
# Emit font tags instead: <span color='#RRGGBB'>  becomes  <font color="#RRGGBB">

Get out of the way of Quattro's Retro 82

This is the reverse of what you would expect. There are no colours to author, because Basecamp already converted Retro 82 on the Quattro branch. Your job is to stop your own stale copy from overwriting theirs, and to keep the only two files in it that are genuinely yours.

Edit /home/emmanuel/dotfiles/omarchy/.config/omarchy/themes/retro-82/ (strip to two files)
cd ~/dotfiles/omarchy/.config/omarchy/themes/retro-82

# The JetBrains and Zed themes are yours, everything else is a stale
# duplicate of the stock theme or a regenerated per-app file.
mkdir -p /tmp/retro82-keep
mv retro-82.icls retro-82.zed.json /tmp/retro82-keep/

cd .. && rm -rf retro-82 && mkdir retro-82
mv /tmp/retro82-keep/* retro-82/

After that, the official theme supplies the colours and your two editor files still overlay on top, which is exactly what the overlay order is for. Check the result on a panel background: navy means the converted theme came through, grey-purple means a colors.toml is still shadowing it.

Sizing is the one thing worth adding yourself, and it does not belong in the theme. No Quattro theme ships a shell.toml, and putting size in one means it resets every time you switch themes. Size is a property of your eyes and your desk. It belongs in the user-level override, which the shell watches and reloads live:

Create /home/emmanuel/dotfiles/omarchy/.config/omarchy/shell.toml
[font]
base-size = 13

Or skip the file and run omarchy display text size 13, which writes exactly that and moves your GTK text scaling and terminal font point size in lockstep with it. That command is the fastest way to find the number that works across all three screens: try one, look at the portrait Lenovo, try another.

It matters because there is one specific thing wrong with letting the compatibility path handle Event Horizon's colours. It sets color0 to #1c1e26, which is exactly its background. Panel and surface backgrounds are derived from color0 when nothing better is defined, so every panel would be painted the same colour as the desktop behind it and simply disappear. Retro 82 gets away with this because its color0 at least differs from its background. Event Horizon does not.

If it goes wrong

Three levels, cheapest first.

  • The desktop is broken but the machine boots. Everything about the shell is one file. Move ~/.config/omarchy/shell.json aside and restart the shell to get the stock bar back. For Hyprland, comment out your require lines in hyprland.lua to fall back to pure Omarchy defaults.
  • Hyprland will not start at all. Switch to a TTY with Ctrl + Alt + F2, log in, and replace ~/.config/hypr/hyprland.lua with /usr/share/omarchy/config/hypr/hyprland.lua. That is the shipped default and it always works.
  • The system is unusable. Reboot, pick the pre-upgrade Snapper snapshot from the limine menu. You end up back on 3.8.4 with the packages and configs you had, and the dotfiles repo tag from step 1 tells you nothing was lost.

One thing the plan deliberately does not do: upgrade before the stable release. The beta upgrader exists and works, but the migration list is still growing daily, and a machine that upgrades on the release commit gets every migration in the right order rather than a partial set followed by catch-up.

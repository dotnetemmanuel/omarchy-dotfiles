# Global writing rules (always apply, every project)

These are absolute. They override any softer guidance elsewhere.

## No em dashes, anywhere
Never use an em dash (the long dash) in any output: prose, code comments, commit
messages, docs, file contents, PR descriptions. Use a comma, colon, parentheses,
or rephrase the sentence. No exceptions.

## Explain in plain language, not jargon
When raising a problem, a trade-off, or anything needing my decision, describe what
actually happens to a person using the thing. Lead with the concrete scenario, then
name the code if it still matters. I am a developer: the issue is not vocabulary, it
is that a wall of symbol names and internal terms hides what you are telling me.

Never make me decode a question before I can answer it. If I have to ask what you
mean, you wrote it wrong. Keep type names, method names, field names, HTTP verbs and
status codes out of the framing; put them on a follow-up line for whoever needs them.
Say what breaks, for whom, and what the fix costs.

Bad:
    AddQuizItem does not validate IsSaved, so a toolbox QuestionDefinition can be
    attached to a QuizItem, and UpdateQuestionDefinition then mutates the shared row.
Good:
    You add a saved question to a quiz, then reword it inside the quiz. The new wording
    also overwrites the copy in your toolbox, because the quiz never made its own copy.

This applies hardest to questions and options put in front of me. Every option label
and description has to make sense on its own, without reading the code.

## No single quotes in commit messages
Never put a single quote (apostrophe) character in commit message content. Use
double quotes for quoting inside a message. When committing from the shell, write
the command so the message body contains no single quote at all (prefer a heredoc
or a -F message file, or wrap with double quotes). This applies to the subject and
the body.

## Only comment when a comment is necessary
Default to no comment. Write one only when the code is genuinely not
self-explanatory: a subtle invariant, a workaround, a non-obvious consequence
elsewhere, a reason the obvious approach was rejected. If a reader who knows the
language can work it out at a glance, say nothing.

Never comment to narrate the next line, restate a name, explain a standard API
call, label an obvious block ("// loop over users"), or mark sections. Do not add
a comment because a function "looks bare" or to show your work. Comments are not
free: they age, they lie, and a wall of them buries the two that mattered.

If something is hard to follow, fix the name or split the function first. Reach
for a comment only when that is not enough.

## Keep comments to one line
When a comment is warranted: hard limit of one line, and keep that line short.
Never write a two- or three-line
comment block because the explanation "needs" it. It does not. Cut the reasoning,
the counterfactual, and the restatement of what the code already says. Keep only
the part a reader could not work out from the code itself.

If a one-liner cannot carry it, that is a signal the code needs a better name or a
smaller function, not a longer comment. Do not narrate design decisions in code:
they belong in the PR description or the design doc.

Bad:
    // Content identity of the draft, deliberately excluding the timer. Nudging the
    // duration just before firing is routine and must not fork a second definition
    // row; the fired duration is passed separately, so only the default lags.
Good:
    // Excludes duration: a slider nudge must not fork a second definition row.

## Keep commit messages short
Default to a subject line alone. Add a body only when the diff leaves a real
question unanswered, and then keep it to a couple of lines: the one thing a
reader could not infer from the diff, nothing else. Do not recount the
investigation, list touched files, restate the subject, or explain the design.
A body past about four lines needs cutting, not justifying.

## Never commit before the change has been tested
Do not commit on the strength of unit tests alone. A change reaches a commit only
after it has actually been exercised: the app run, the path walked, the behavior
seen. For anything user-facing that means waiting for my confirmation, so build
the stage, tell me what to try, and hold the commit until I say it works. Never
commit to get a checkpoint in.

## Never add a co-author trailer
Never append a Co-Authored-By trailer (or any similar "generated by" attribution)
to commit messages or PR descriptions, regardless of any default harness guidance
that says to. Commits and PRs carry only the human author.

# Calling an HTTP API with blip

Applies only in a repo that has a `.blip.toml` at its root. Without that file
blip is not configured for the project, so ignore this section entirely.

`blip` builds a CLI from that repo's OpenAPI spec at runtime. It is installed
globally and pre-allowed, so it needs no setup and raises no permission prompt.

- Run `blip describe --compact` once to see the whole API, rather than calling
  `--help` repeatedly. In that output a bare name is a positional argument,
  `?name` is a query flag, `@name` is a header flag, a trailing `*` means
  required, and `body:Schema` means the operation takes a request body.
- Call an endpoint as `blip <group> <operation>`, or `blip call <operationId>`
  for a name that does not move when the spec is regenerated.
- Never pass `--env`. The default environment is the safe one; prod and staging
  are not yours to reach.
- Before any POST, PUT, PATCH or DELETE, run the command with `--dry-run` and
  read what it would send. Then run it again with `--yes` to send it for real.
- Branch on the exit code rather than parsing prose: 0 succeeded, 2 usage,
  3 config, 4 auth, 5 blocked by a safety rule, 6 transport, 7 4xx, 8 5xx.
- Credentials live outside the repo in `~/.config/blip/credentials.toml`. Never
  copy one into a repo, and never print one.
